## 二、pytest 是怎么"发现"测试的

pytest 按固定规则自动收集（配置在 `Back_End/pytest.ini`）：

| 对象 | 规则 |
| --- | --- |
| 文件 | `test_*.py` 或 `*_test.py` |
| 类 | 以 `Test` 开头，且**不能有 `__init__`** |
| 函数/方法 | 以 `test_` 开头 |

不需要继承任何基类、不需要注册，写个 `test_` 函数就能跑 —— 这是 pytest 比 `unittest` 好用的第一点。
断言直接用 Python 的 `assert`，pytest 会**重写断言**并在失败时打印每个子表达式的值：

```
E       assert 3 == 4
E        +  where 3 = <Calculator object>.add(1, 2)
```

## 四、fixture 深入讲解（课案重点）

### 1. 为什么需要 fixture

```python
# 没有 fixture：每个测试都要重复准备代码
def test_a():
    calc = Calculator()
    ...
def test_b():
    calc = Calculator()      # 复制粘贴
    ...
```

fixture 把"准备代码"抽出来，按名字注入，并且**自动处理清理**。

### 2. scope：决定 fixture 多久创建一次

| scope | 频率 | 适用 |
| --- | --- | --- |
| `function`（默认） | 每个测试函数一次 | 绝大多数场景，隔离性最好 |
| `class` | 每个测试类一次 | 类内共享的准备工作 |
| `module` | 每个测试文件一次 | 文件内共享的较重资源 |
| `session` | 整个测试会话一次 | 数据库引擎、启动一次的服务 |

**先想清楚"共享是否安全"再改 scope** —— 共享可变状态是最常见的测试互相干扰来源。

### 3. yield：Setup / Teardown

```python
@pytest.fixture()
def temp_file():
    path = ...
    path.write_text("test data")   # Setup
    yield path                     # 交给测试
    path.unlink()                  # Teardown（测试失败也会执行）
```

本目录的 `temp_file` 使用 `tempfile.gettempdir()` 生成固定但唯一的路径，
比课案里写死 `temp.txt` 更不容易互相干扰。

### 4. 参数化 fixture vs parametrize

```python
@pytest.fixture(params=[2, 4, 8])          # 参数化 fixture：测试环境跑 3 遍
def any_precision(request):
    return Calculator(precision=request.param)

@pytest.mark.parametrize("a,b,exp", [(1,2,3)])   # 参数化入参：数据驱动
def test_add(a, b, exp): ...
```

经验：**被测数据用 `parametrize`，被测环境/依赖用参数化 fixture**。

## 五、写测试的几条经验（来自实战）

1. **一个测试只验证一件事**：名字要能当文档读，例如 `test_patch_does_not_change_other_fields`。
2. **测试之间必须互不依赖**：任何顺序都能通过（`pytest -p no:randomly` / `--ff` 都会暴露问题）。
3. **不要测实现细节**：测"输入 → 输出"的行为，重构才不会大面积改测试。
4. **边界值是 bug 高发区**：0、空列表、最大值、None、超长字符串、特殊字符。
5. **异常也要断言**：用 `pytest.raises`，否则"没抛异常"和"抛了别的异常"都会被误判通过。
6. **测试要快**：单测不依赖网络与外部服务（本项目所有测试都不需要 MySQL/Redis）。
7. **CI 里必须跑**：本地能过不算过，见 `08_代码格式化/README.md` 的 GitHub Actions 示例。
